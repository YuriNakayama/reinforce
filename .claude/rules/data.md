# Data Layout Rules

`data/` is the data layer of the repository. **Actual contents are git-untracked and managed by DVC + S3.** Only `*.dvc` / `*.md` / `.gitkeep` / `.gitignore` files are tracked by git.

## Top-level layout (4 fixed layers)

Do **not** create any directory directly under `data/` other than the four layers below. When adding a new use case, classify it into one of these four layers and create a subdirectory under it.

```
data/
├── lake/        Raw data (collected as-is, no processing)
├── processed/   Pre-processed data (intermediate artifacts)
├── mart/        Curated data for training/evaluation (aggregated tables, etc.)
└── output/      Final pipeline artifacts
```

| Layer | Nature | Examples |
|---|---|---|
| `lake/` | Immutable, original. Re-acquisition required if lost | `lake/demonstrations/` (expert trajectories, offline-RL datasets) / `lake/replays/` (episode dumps from external sources) |
| `processed/` | Intermediate data derived from lake | Parsed trajectories → per-step parquet |
| `mart/` | Curated data read directly during training/evaluation | `mart/offline/case1/{train,val}.parquet` (offline-RL only; online RL has no mart) |
| `output/` | Pipeline execution results, regenerable | `output/models/<family>/<case>/runs/<run_id>/` (checkpoints, metrics.json, eval) / `output/experiment/` (aggregated plots, JSON) / `output/benchmark/` (env throughput results) |

## How to choose a layer

- **Need re-acquisition if lost → `lake/`**
- **Reproducible by re-running code → `output/`**
- **Between lake and output, consumed by other pipelines → `processed/` or `mart/`**
- When in doubt: **inputs default to `lake/`, outputs default to `output/`**

## Subdirectory naming

- Directly under each layer: split by **use-case domain** (`demonstrations/`, `replays/`, `offline/`, `models/`, `experiment/`, `benchmark/`)
- Below the domain: split by **family / case** (`models/ppo/case1/`, `offline/case1/`)

## DVC management

- Track each directory under lake / mart / output with `dvc add` at the **directory** level. Commit only the generated `*.dvc` files to git
- S3 remote is named `s3`; the bucket will be created by Terraform (`infra/module/application/dvc_remote`, not yet ported — see `.claude/rules/infra.md`) and wired up per-machine via `dev/dvc setup`. `.dvc/` itself is created once with `dvc init` + `dvc remote add -d s3 s3://<bucket>/remote` after the bucket exists
- Fetch real contents with **`dev/dvc pull <target>.dvc`** — always name the target.

> **A bare `dev/dvc pull` deletes tracked data.** DVC does not auto-discover
> `.dvc` files under `data/` here (the tree is `.gitignore`d apart from the
> stubs), so it concludes nothing is tracked and removes the "orphaned"
> directory. Recovery is `dev/dvc pull data/output/models.dvc
> --force`, which re-fetches from S3 — but only because the blobs are in S3.
> Name the target and this never comes up.

## .gitignore behavior

`.gitignore` ignores everything under `/data/**` **except**:

- `*.dvc` (DVC tracking files)
- `*.md` (README and similar)
- `.gitignore` (including those auto-generated by DVC)
- `.gitkeep` (placeholder for empty directories)

Real data (parquet, json, json.gz, png, model weights) must never be committed. Treat an accidental data commit as a rewrite-history incident, not a follow-up cleanup.

## Prohibitions

- **No directories directly under `data/` other than lake / processed / mart / output**
- Never commit real data to git (manage via `.dvc` files)
- Use repository-root-relative paths (`data/...`), not hardcoded absolute paths
