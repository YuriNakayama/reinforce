# JAX 化と GPU 検証の結果（kaggriculture より）

> 出典: kaggriculture リポジトリ `docs/plans/simulator/jax-gpu.md`（2026-08）。
> 対象は `kaggle-environments` 上の農場シミュレータ。その JAX 移植が
> このリポジトリの `backend/src/simulate/jaxenv/` にテンプレートとして残っている。
> 当時の等価性テスト・依存関係の経緯など、ここで再現できない節は削除した。
>
> **結論: CUDA では 42,900 倍に高速化した。Apple Metal では逆に遅くなった。**
> GPU バックエンドによって結果が正反対になるため、「GPU なら速い」とは言えない。

## 1. 結論サマリ

| 実行環境 | batch | env-steps/s | 公式 engine 比 |
|---|---|---|---|
| 公式 engine（`env.run`） | 1 | 850 | 1x |
| interpreter 直接呼び出し | 1 | 13,337 | 16x |
| JAX / CPU（M2 Max） | 1 | 50,973 | 60x |
| JAX / CPU（M2 Max） | 8192 | 276,042 | 325x |
| **JAX / Metal GPU** | 1 | 219 | **0.26x（公式より遅い）** |
| **JAX / Metal GPU** | 64 | 922 | **1.1x** |
| **JAX / CUDA（RTX 4090）** | 64 | 226,014 | 266x |
| **JAX / CUDA（RTX 4090）** | 8192 | 25,942,145 | 30,520x |
| **JAX / CUDA（RTX 4090）** | **65536** | **36,489,836** | **42,929x** |
| JAX / CUDA（RTX 4090） | 262144 | 31,956,572 | 37,596x（飽和後） |

- CUDA では batch 65536 で 3,650 万 env-steps/s に達し、それ以上は頭打ちになった。
- Metal では CPU の約 118 分の 1。batch 256 以上は 24 step すら 2 分で終わらず計測を打ち切った。
- 同じ batch 64 で CUDA は Metal の 245 倍だった。

## 2. 検証環境

| 項目 | ローカル | CUDA |
|---|---|---|
| マシン | Apple M2 Max、GPU 30 コア、32 GB | RunPod RTX 4090（24GB）/ Community Cloud |
| バックエンド | `jax-metal` 0.1.1 + JAX 0.4.34 | JAX 0.11.0 + `jax[cuda12]` |
| ドライバ | — | 550.54.15 / CUDA 12.4 |
| コスト | — | $0.34/h × 約 14 分 ≈ $0.08 |

`jax-metal` は JAX 0.11 と非互換で、0.4.34 に固定して初めて動いた。
**`jax-metal` をリポジトリの venv に入れてはいけない。** 入れると
`jax.devices()` が METAL を返し、既存テストがその上で走ってしまう。

## 3. Metal が遅い原因は scatter

同一コードを 3 バックエンドでマイクロベンチした（B=64、50 回）。

| 操作 | CPU | Metal GPU | CUDA（4090） |
|---|---|---|---|
| 要素演算 `(B,2,10,10)` | 1.5 ms | 24.6 ms | 6.0 ms |
| **`.at[].set` scatter** | **1.0 ms** | **222.7 ms** | **5.7 ms** |
| scatter / 要素演算 の比 | 0.7x | **9.1x** | **0.95x** |

CUDA では scatter が要素演算と同じコストで済むが、Metal は 9.1 倍かかる。
`jax-metal` に効率的な scatter 実装が無いのが原因で、batch を増やしても
このレイテンシは減らない。

GPU そのものは正常に動いていた（2048³ 行列積）。

| バックエンド | 時間 | GFLOP/s |
|---|---|---|
| numpy CPU | 10.30 ms | 1,668 |
| Metal GPU | 2.91 ms | 5,903 |
| CUDA（RTX 4090） | 0.40 ms | 43,269 |

**教訓**: タイルや実体を「特定の要素だけ書き換える」環境は scatter の塊になる。
GPU に載せる前に、対象バックエンドで scatter と要素演算の比を測る。

## 4. 移植の範囲と等価性

移植したのはゲームの決定論的なコア（作物・移動・市場の一部・日次処理）だけで、
雇用・家畜・土地購入などは未実装だった。**速度はもう足りており、次の投資先は
忠実度**という結論になった。

再実装なので等価性は構造的に保証されず、実測で確認した。

| 検証 | 結果 |
|---|---|
| 市場価格 9 商品 × 223 在庫点 | 2,007 点すべて公式と一致 |
| 15 日 = 360 step の状態（所持金・種・在庫） | 全 step 一致 |
| batch 1 と batch 16 | 同一結果 |
| batch 内の環境同士の干渉 | 無し |
| CUDA 上での同じ 15 日エピソード | CPU・公式と同じ値（float32 の丸めを含む市場価格も一致） |

## 5. 移植中に見つかった落とし穴

**乱数の消費順が盤面に依存していた。** 雑草の生成が同じ RNG を先に消費し、
その回数は空きタイル数に等しかった。そのためイベントのスケジュールは seed だけでは
決まらず、事前にテーブル化できなかった。等価性の比較は、その乱数要素を両エンジンで
無効化した決定論的コアで行った。

**RL への読み替え**: 環境の乱数を `jax.random.PRNGKey` で明示的に分岐させる設計に
するなら、元実装の「どの処理が何回乱数を引くか」を先に調べる。消費順の違いは
例外を出さずに結果だけを変える。

## 6. 用途別の使い分け（当時の結論）

| 用途 | 推奨 | 根拠 |
|---|---|---|
| 本番と同じ経路での検証 | 公式 engine | ルール乖離ゼロ |
| ローカルの大量評価 | interpreter 直接呼び出し | 13k steps/s、ルール乖離ゼロ |
| Mac 上でのパラメータ探索 | JAX / CPU | 276k steps/s。Metal は使わない |
| RL 学習・大規模自己対戦 | **JAX / CUDA** | 36.5M steps/s |

RTX 4090 では batch 65536 前後が最適で、262144 では低下した。

## 7. RunPod で計測したときの注意

- RunPod SDK にはログ取得 API が無い。pod 内の stdout だけに出した結果は回収できないので、SSH で対話実行するのが確実だった。現在の `dev/runpod` は S3 への進捗・ログ転送でこれを補っている。
- イメージの `python` と `pip` の Python バージョンが違い、`python -m` が `ModuleNotFoundError` になった。実行するインタープリタのパスを明示する。
- pod は必ず終了させる。onstart 側の watchdog、ランチャーの `finally`、手動の terminate を合わせた三重の停止経路にした。

## 8. このリポジトリでの再現

```bash
# 当時の公式 engine / 直接呼び出しはここに無いので JAX のみ計測する
uv run --directory backend python -m simulate.jaxenv.benchmark \
    --steps 720 --batches 1 64 1024 8192
```
