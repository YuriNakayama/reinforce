# 評価基盤の教訓（kaggriculture より）

> 出典: kaggriculture リポジトリ `docs/plans/simulator/design.md`（2026-08）。
> 対象は Kaggle の 2 人対戦農場シミュレータ（`kaggle-environments 1.32.6`）。
> 実装計画・CLI・テスト構成など、このリポジトリで再現できない節は削除し、
> **RL の評価にも通じる計測値と教訓だけ**を残している。固有名は当時のまま。

## 1. 実測した前提

| 事項 | 実測値 | 当時の判断 |
|---|---|---|
| 1 エピソード（720 turn） | 約 1.3 秒 | Python の素実装で評価には十分 |
| 8 並列（`ProcessPoolExecutor`, spawn） | 8 ep / 1.5 秒 | プロセス並列がそのまま効く |
| 1 エピソードのリプレイ（`env.toJSON()`） | 約 4.8 MB | 全 ep の保存は非現実的。既定は保存しない |
| 1 ターンの制限時間（`actTimeout`） | 1 秒 | ローカルでも超過検出が必須 |
| クラッシュ時・timeout 時の `status` | どちらも `DONE` | status では失敗を判定できない |

## 2. 最重要の教訓: 失敗は報酬にしか現れない

当時の engine は、例外を投げたエージェントも時間切れのエージェントも
`status=DONE` で完走扱いにし、不正な行動は無警告で捨てた。その結果、
**壊れたエージェントが「弱いエージェント」に見える**。

失敗検出は 3 系統を併用した。

1. **クラッシュ**: デバッグモードで実行を `try/except` で包み、例外を捕まえたら壊れていると断定する。
2. **時間超過**: ステップごとの所要時間ログだけが情報源。制限の半分超を警告、超過を失敗として集計する。
3. **無視された行動**: engine に渡す前に行動を自前で検証し、「意図した行動」と「適用された行動」の差を数える。

**RL への読み替え**: 報酬曲線が伸びないとき、それが「学習が遅い」のか
「行動が環境に届いていない」のかは報酬だけでは区別できない。環境ラッパーで
行動の合法性・NaN・エピソード長の異常を別カウンタとして記録し、
`metrics.json` に並べて出すと同じ効果が得られる。

## 3. 並列評価の設計

- ワーカー内で環境を作り、**軽量な結果 dataclass だけを返す**。環境オブジェクトを返すと数 MB の pickle が並列度ぶん転送される。
- 並列度 1 に落とせるようにしておく（デバッガを使うため）。
- seed は `seed_base + i` で決定論的に割り当て、結果ファイルに記録して再現可能にする。

## 4. 実装中に見つかった落とし穴

| 発見 | 教訓 |
|---|---|
| engine 内部のエージェント呼び出しは `(action, log)` のタプルを返し、組み込みエージェントは action 単体を返した | 検証器が 600 件の誤検出を出した。ラッパーは戻り値の形を実物で確かめる |
| 組み込みの `random` エージェントは引数なしの `random.Random()` を使い、環境の seed で制御できなかった | 再現性テストは決定論的なエージェント同士でしか成立しない。RL でも評価相手・評価方策の RNG を明示的に seed する |
| 所要時間は wall-clock で、pytest の並列ワーカーが CPU を奪い合うと膨らんだ | 時間の閾値テストは緩い境界にし、厳密な判定はカウンタ側で行う |

## 5. 評価基盤が実際に役立った例

初版のエージェントは移動せず 1 タイルしか耕さない実装だったが、例外は出なかった。
評価基盤は勝率 66.7% と報告し、修正後は 100% になった。行動検証のカウンタは
検証器自身のバグ（誤検出 600 件）も即座に露出させた。**スコアにしか現れない
バグを、スコア以外の指標で可視化する**という設計が狙いどおりに機能した。
